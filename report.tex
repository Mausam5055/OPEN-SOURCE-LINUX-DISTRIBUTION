\chapter{Introduction \& Overview}

When we think about huge apps or websites today, we usually picture big tech companies building everything behind closed doors. But actually, a massive part of the internet runs on something completely different: Open Source software. Open source isn't just about getting free stuff; it's a totally different way of sharing knowledge. When developers around the world can look at, fix, and improve the same code, things get built faster and become way more secure than if they were hidden away.

For this project, I chose to look into **Git**. Even though I use Git all the time to save my code for classes, I never really stopped to think about how it actually works or why it was made. We just type \texttt{git commit} without knowing the history behind it. In this report, I will talk about where Git came from, why its open-source license matters, and share some shell scripts I wrote to see how things run on Linux.

\section{Chosen Software: Git}

Git is what we call a distributed version control system. Basically, it's a tool that lets developers track changes to their files over time, work together on group projects without deleting each other's work, and easily undo mistakes if something breaks. Unlike older tools, Git doesn't need to connect to one main central server to do its job. Everyone gets their own full, working copy of the project history right on their laptop. 

Git is basically everywhere now. Websites like GitHub and GitLab host millions of open-source projects using it. But what makes it so cool isn't just that it's popular---it's how it was made. It wasn't built by a corporation to sell user subscriptions. It was coded really quickly just to fix a genuine problem the Linux team was having, and then it was shared with the entire world for free.

\chapter{Research Analysis}

\section{Part A --- Origin and Philosophy}

\subsection{The Problem Before Git}
Before Git existed, managing code versions was pretty painful. People used systems like CVS or SVN. These were centralized, meaning the code lived on one main server. If you wanted to save your work, you needed an internet connection to that server. If the server ever went down or crashed, nobody could work. Doing simple things like branching (splitting code to test a new feature) caused massive headaches.

The story of Git actually starts directly with Linux. Linus Torvalds and his team were building the Linux operating system using a closed-source tool called BitKeeper because the company let them use it for free. But in 2005, there was some drama. Someone in the community tried to reverse-engineer how BitKeeper worked, so the company got mad and revoked the free licenses. Suddenly, the Linux team had no way to manage their massive project.

\subsection{The Origin Story of Git}
Instead of paying for an expensive enterprise tool or going back to the old, clunky centralized systems, Linus decided to just write his own. In April 2005, he started coding Git. Because he knew exactly what the Linux team needed, he got the first version working in just a couple of weeks. 

He wanted it to follow a few simple rules:
\begin{itemize}
    \item \textbf{Speed}: It had to be incredibly fast because the Linux kernel has millions of lines of code.
    \item \textbf{Distributed}: No single point of failure; every developer needed their own full copy.
    \item \textbf{Data Safety}: It uses special cryptographic hashes so that once code is saved, it can't be secretly corrupted or changed.
\end{itemize}

\subsection{License Analysis: GPL v2}
Git uses the GNU General Public License version 2 (GPL v2), which is the exact same license used for Linux. The Free Software Foundation says truly "free" software needs four freedoms: the freedom to run the program, the freedom to study and change the code, the freedom to share it, and the freedom to share your improvements. Git checks all those boxes perfectly. 

A lot of people think companies can't sell open-source software, but they can! The catch is that GPL is a "copyleft" license. If a company modifies Git and shares it, they have to share their new source code under the GPL too. You can't just take the community's hard work, add a feature, and hide the code to sell it. 

This is very different from the MIT License, which is way more relaxed and lets people do whatever they want (even close the source code) as long as they don't sue the original creator. Because Git is so important to how we build software, the GPL is the perfect choice to stop giant companies from monopolizing it. If I were building a big tool today, I would definitely pick GPL to protect it.

When developers talk about "free as in beer versus free as in speech", they mean two different things. A free app on your phone is "free as in beer": it costs zero dollars, but it's locked down and you don't actually own it. Open-source software is "free as in speech": you have the liberty and rights to see how it works and change it.

\subsection{The Ethics of Open Source}
Ethically, I think foundational tools like operating systems, web servers, and databases should always be open source so everyone benefits. But I also think it's okay for specific apps, like video games, to be closed source so developers can actually make a living. 

It is totally fine for huge companies to use open source to make money, as long as they give back by funding the projects or hiring the developers who maintain them. In programming, we say we "stand on the shoulders of giants." This just means we aren't starting from scratch. When I write a script, it runs on Linux, using tools someone else built years ago. We literally build everything on top of the free gifts left by past developers.

\section{Part B --- Linux Footprint}

This section briefly looks at how Git lives and behaves on a standard Linux computer.

\subsection{Installation Method}
Installing Git on a Linux machine like Ubuntu is super easy. You just use the default APT package manager:
\begin{lstlisting}[language=bash]
sudo apt update
sudo apt install git
\end{lstlisting}

\subsection{Directory Structure}
The main executable program sits cleanly in \texttt{/usr/bin/git}. Whenever you use it in a project folder, it creates a hidden \texttt{.git} folder right there to store all the actual tracking history, keeping everything isolated from the rest of your system. Your personal settings, like your email and name, are kept quietly in a \texttt{\~{}/.gitconfig} file inside your home folder. 

\subsection{User and Permissions}
Git operations run purely under the permissions of whoever is logged in. It never demands root (admin) privileges to do daily commits or formatting. This matters a lot for security because if a normal user accidentally runs a destructive Git command, they can only ruin their own files, not the whole server.

\subsection{Service Behavior}
Instead of running as a heavy background service constantly eating up RAM, Git is just a Command Line Interface (CLI) tool. It only wakes up, processes your command, and immediately goes back to sleep when you type something.

\subsection{Update Model}
Security patches and bug fixes are continuously maintained by the open-source community. These updates are then safely bundled and handled securely through the OS package manager (like \texttt{apt upgrade}), so you never have to hunt down sketchy installers from the internet.

\section{Part C --- The FOSS Ecosystem}

\subsection{Dependencies}
Since Git was built in C, it depends heavily on standard GNU system tools. It also relies on external libraries like \texttt{OpenSSL} to handle secure internet connections and \texttt{zlib} for zipping files efficiently.

\subsection{What Git Enables \& The Web Ecosystem}
Git completely changed the software industry. It directly enabled platforms like GitHub and GitLab. More importantly, it forms the backbone of the modern web ecosystem (like LAMP stacks). Without Git tracking exactly what changed in the code, automated tools wouldn't know when to safely test or deploy new updates to a live website. It acts as the invisible glue holding DevOps together.

\subsection{Community and Governance}
Despite running massive platforms like GitHub, Git's own internal development community is incredibly old-school. Updates and patches are still discussed by developers passing plain-text emails back and forth on a giant mailing list. It functions as an open, transparent dictatorship overseen by a core maintainer.

\section{Part D --- Open Source vs Proprietary}

We can compare Git with an older proprietary tool like Microsoft's Team Foundation Version Control (TFVC).

\begin{center}
\begin{longtable}{|p{3cm}|p{6cm}|p{6cm}|}
\hline
\textbf{Feature} & \textbf{Git (Open Source GPL)} & \textbf{TFVC (Proprietary)} \\
\hline
\textbf{Cost} & 100\% Free. You can use it as much as you want without user limits. & Starts free but has very expensive paid tiers for bigger enterprise setups. \\
\hline
\textbf{Security} & Code is double-checked by thousands of smart people online. & Only Microsoft employees can look at the code to fix internal bugs. \\
\hline
\textbf{Support} & You search Google or Reddit, and read community forums. & You get official corporate IT support from Microsoft. \\
\hline
\textbf{Flexibility} & You can do everything entirely offline on a laptop on an airplane. & You need to be connected to the central server to do major work. \\
\hline
\textbf{Control} & You fully control your own local codebase history. & The central server controls the master history timeline. \\
\hline
\end{longtable}
\end{center}

Overall, I would absolutely recommend Git for any real-world scenario. It's free, it works fully offline, and essentially everyone uses it. Even Microsoft eventually gave up pushing TFVC and switched their own Windows development teams over to Git. While I probably won't be writing raw C code to contribute to Git's core anytime soon, I am happy to support open source by using it properly and sharing my own projects freely!

\section{Script 1: System Identity Report}
This is a simple script that grabs basic info about the computer. It uses variables and the \texttt{\$(command)} syntax to run things like \texttt{uname} and \texttt{uptime}, and then prints them out to introduce the system.

\begin{lstlisting}[language=bash, caption=01\_system\_identity.sh]
#!/bin/bash
# Script 1: System Identity Report
# Author: Mausam Kar | Course: Open Source Software

# --- Variables ---

\section{Script 2: Package Inspector}
This script checks if a piece of software is installed. It uses an `if-else` block to look for the application package, and then uses a `case` statement to print out a fun fact depending on what the software is.

\begin{lstlisting}[language=bash, caption=02\_package\_inspector.sh]
#!/bin/bash
# Script 2: FOSS Package Inspector

PACKAGE="git"

if dpkg -l "$PACKAGE" &>/dev/null || command -v "$PACKAGE" &>/dev/null; then
 echo "$PACKAGE is installed."
 if command -v dpkg &>/dev/null && dpkg -s "$PACKAGE" &>/dev/null; then
  dpkg -s "$PACKAGE" | grep -E '^Version|^Description' | head -n 2
 else
  echo "Version: $($PACKAGE --version)"
 fi
else
 echo "$PACKAGE is NOT installed."
fi

case $PACKAGE in
 httpd|apache2) echo "Apache: the web server that built the open internet" ;;
 mysql) echo "MySQL: open source at the heart of millions of apps" ;;
 git) echo "Git: decentralized tool that enabled global code collaboration" ;;
 vlc) echo "VLC: media player that proves open source can handle any format" ;;
 firefox) echo "Firefox: browser fighting for a free, open, and private web" ;;
 *) echo "$PACKAGE: Another great tool in the open source ecosystem" ;;
esac

echo ""
read -p "Press [Enter] to exit..."
\end{lstlisting}

\section{Script 3: Disk and Permission Auditor}
This script uses a \texttt{for} loop to check a list of folders. It runs commands like \texttt{ls -ld} and \texttt{df -h}, and then uses \texttt{awk} and \texttt{cut} to slice up the text so we only see the exact file sizes and permissions we actually care about.

\begin{lstlisting}[language=bash, caption=03\_disk\_auditor.sh]
#!/bin/bash
# Script 3: Disk and Permission Auditor

DIRS=("/etc" "/var/log" "/home" "/usr/bin" "/tmp")
echo "Directory Audit Report"

for DIR in "${DIRS[@]}"; do
 if [ -d "$DIR" ]; then
  # Extract Permissions
  PERMS=$(ls -ld "$DIR" | awk '{print $1, $3, $4}')
  # Check directory size using du and cut
  SIZE=$(du -sh "$DIR" 2>/dev/null | cut -f1)
  # Check filesystem storage usage using df and awk
  FS_USAGE=$(df -h "$DIR" 2>/dev/null | awk 'NR==2 {print $5}')
  
  echo "$DIR => Permissions: $PERMS | Size: $SIZE | Disk Used: $FS_USAGE"
 else
  echo "$DIR does not exist on this system"
 fi
 done

GIT_CONFIG="$HOME/.gitconfig"
if [ -f "$GIT_CONFIG" ]; then
  GIT_PERMS=$(ls -ld $GIT_CONFIG | awk '{print $1, $3, $4}')
  echo "Git config ($GIT_CONFIG) exists. Permissions: $GIT_PERMS"
else
  echo "Git config ($GIT_CONFIG) does not exist."
fi

echo ""
read -p "Press [Enter] to exit..."
\end{lstlisting}

\section{Script 4: Log File Analyzer}
This script takes arguments from the command line (\texttt{\$1} and \texttt{\$2}). It uses a \texttt{while read} loop to scan through a huge file line by line to count how many times a word like "error" shows up, which is great for finding bugs.

\begin{lstlisting}[language=bash, caption=04\_log\_analyzer.sh]
#!/bin/bash
# Script 4: Log File Analyzer

LOGFILE=$1
KEYWORD=${2:-"error"}
COUNT=0

if [ ! -f "$LOGFILE" ]; then
 echo "Error: File $LOGFILE not found."
 read -p "Press [Enter] to exit..."
 exit 1
fi

RETRY=0
while true; do
  if [ -s "$LOGFILE" ]; then break; fi
  echo "Warning: File is currently empty. Retrying in 2 seconds..."
  sleep 2
  RETRY=$((RETRY + 1))
  
  if [ $RETRY -ge 3 ]; then
    echo "Error: File is still empty. Exiting."
    read -p "Press [Enter] to exit..."
    exit 1
  fi
done

while IFS= read -r LINE; do
 if echo "$LINE" | grep -iq "$KEYWORD"; then COUNT=$((COUNT + 1)); fi
done < "$LOGFILE"

echo "Keyword '$KEYWORD' found $COUNT times in $LOGFILE"

if [ $COUNT -gt 0 ]; then
  echo "--- Last 5 Matching Lines ---"
  grep -i "$KEYWORD" "$LOGFILE" | tail -n 5
fi

echo ""
read -p "Press [Enter] to exit..."
\end{lstlisting}

\section{Script 5: Manifesto Generator}
This is an interactive script that uses \texttt{read} to ask the user questions while it runs in the terminal. Once it gets your answers, it glues them together into a paragraph and uses \texttt{>>} redirection to save it all into a new \texttt{.txt} file.

\begin{lstlisting}[language=bash, caption=05\_manifesto\_generator.sh]
#!/bin/bash
# Script 5: Open Source Manifesto Generator

echo "Answer three questions to generate your manifesto."
read -p "1. Name one open-source tool you use every day: " TOOL
read -p "2. In one word, what does 'freedom' mean to you? " FREEDOM
read -p "3. Name one thing you would build and share freely: " BUILD

DATE=$(date '+%d %B %Y')
OUTPUT="manifesto_$(whoami).txt"

echo "### My Open Source Manifesto ###" > "$OUTPUT"
echo "Date: $DATE" >> "$OUTPUT"
echo "I believe in open source because tools like $TOOL make my daily life easier." >> "$OUTPUT"
echo "To me, true freedom means $FREEDOM, which is exactly the core philosophy of open source." >> "$OUTPUT"
echo "If I had the chance to contribute, I would build $BUILD and share it!" >> "$OUTPUT"

echo "Manifesto saved to $OUTPUT"
cat "$OUTPUT"

echo ""
read -p "Press [Enter] to exit..."
\end{lstlisting}
